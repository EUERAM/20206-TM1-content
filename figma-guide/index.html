UI fundamentals · 01 · Color and palettes

Give every color a role

Do not choose colors only by personal taste. Define what each color communicates and where it belongs. As a starting exercise, try the 60–30–10 rule: 60% dominant color for the background, 30% secondary color to distinguish cards or sections, and 10% accent for the primary action. Treat this as a prompt, not a formula every interface must follow.

  • Create semantic styles such as Surface / Base, Text / Primary, Action / Primary, and Status / Error.
  • Use red for errors or destructive actions when the context calls for it. Do not rely on color alone; pair it with a label or icon.
  • Ensure sufficient contrast between text and its background. Check contrast with a contrast checker. Aim for a WCAG ratio of at least 4.5:1 for normal text and 3:1 for large text.

Try it: Start with a calm background, separate content with a subtle surface, and reserve one accent for the main action. In a banking app, a “Transfer money” button should stand out without competing with every transaction.

UI fundamentals · 02 · Typography

Make reading order obvious

Start with a readable typeface. If you use two families, reserve one for headings and one for long-form text. If you are unsure, one family with a few carefully chosen weights is a reliable starting point.

  • Define named text styles for roles such as heading, subheading, body, and label.
  • Make the difference between a heading and body copy clear in both size and weight.
  • Start around 16 px for primary on-screen body text, then check readability at the actual device size. Smaller supporting labels still need to be legible.

Try it: Create a clear title, quieter supporting information, and comfortable body copy. On a property page, the property name should be easier to spot than its address or secondary details.

UI fundamentals · 03 · Microinteractions

Show that the interface heard the user

Every click or tap should receive a clear response. Give immediate feedback and use animation only when it helps explain a state change or relationship.

  • Design the states you need: default, hover on pointer devices, focus, pressed, disabled, and loading.
  • Use brief transitions to make state changes clear; reserve more elaborate motion for explaining where an element comes from or goes.

Try it: After saving, change the button label to “Saved” and show a confirmation. The state change communicates the result without decorative animation.

UI fundamentals · 04 · Navigation

Help users understand where they are

Clear navigation answers three questions: “Where am I?”, “Where did I come from?”, and “Where can I go?” Use familiar patterns when they fit the product, and give controls understandable labels.

  • Mark the current section with more than one cue, such as color plus weight or an indicator.
  • Use breadcrumbs when pages have a hierarchy and users need to move back up a level.
  • Do not treat the “three-click rule” as a law. Prioritize understandable structure, clear labels, and easy-to-find actions.

Try it: Highlight the current page in the navigation and, on a deeply nested page, show a path such as “Home / Computing / Laptops” so users can return to a parent category.

UI fundamentals · 05 · Mobile and desktop

Adapt the interface to the context

Mobile is not simply a narrow desktop screen: available space, posture, and interaction all change. Prioritize the content and adapt the layout to the task.

  • Touch screens have no hover state. Do not hide important actions behind hover.
  • Make touch targets comfortable to use; 44 × 44 px is a useful starting reference, especially for frequent actions.
  • Consider the thumb zone for common mobile actions. A bottom navigation bar is not right for every product or task.
  • Desktop can make room for columns and sidebars. Mobile often benefits from stacking content and rethinking the menu. Test both layouts.

Try it: Identify the essential content, decide what should rearrange or collapse, then check that important tasks remain easy in both layouts.

01 · Get oriented

The Figma workspace

The editor is organized around the canvas. Select an object to see the controls that apply to it; the right panel changes depending on what you select and which mode you are using.

Top toolbar

Switch between design tools: move and scale, frames, shapes, pen, text, comments, and resources such as components. Use the play/present control to preview a prototype.

Pages & left panel

Pages organize a file into large chapters. The Layers view shows the selected page's frames and objects in their parent-child hierarchy. Assets provides access to reusable components and libraries.

Canvas

The central work area where you arrange frames and design objects. Pan around, zoom, and select objects here. The canvas is not itself a screen—frames define screens and containers.

Right properties panel

Design controls edit position, size, layout, appearance, and export settings. Prototype controls connect views and configure interactions. Dev Mode presents implementation-oriented inspection details.

Bottom controls

Find zoom and view controls, help, and collaboration tools. Some controls move or change with Figma updates and window size.

Tip: If a property seems to be missing, select the object first, then check the active right-panel tab and the current mode.

02 · Plan before drawing

Create a useful file structure

Give the file a name that tells a teammate what it contains. Use a project or course name, a clear product or assignment name, and a state or version when needed.

Name pages for their purpose. For a first responsive interface, keep related screens easy to find:

File MT1 — Campus Companion
Page 00 — Cover
Page 01 — Design System
Page 02 — Desktop UI
Page 03 — Mobile UI

Separate desktop and mobile pages when it helps you work, present, or review each layout. If the project is small, or both layouts need to be compared side by side, keep them together on one page in clearly named sections. The point is to make the file easy to navigate—not to follow a rigid page count.

Use a consistent naming pattern for frames too: Desktop / Home, Desktop / Search, Mobile / Home. Avoid names such as Frame 24, Final final, or New page 2.

03 · Reuse decisions

Styles keep a design consistent

A style is a named, reusable design choice. It lets you apply the same color or text treatment again and update its definition without hunting through every screen. Shared styles also make decisions visible to collaborators.

Reusable style types

  • Color styles: name by use, such as Text / Primary, Surface / Default, or Action / Primary—not only by a hex value.
  • Text styles: define a typeface, weight, size, line height, and (when needed) letter spacing for a role such as Heading / H1 or Body / Regular.
  • Effect styles: share treatments such as a shadow, when repeated consistently in the interface.

Name styles by their role

Use names that explain where a value belongs, such as Text / Primary or Heading / H1. Clear names make the system easier to scan and help collaborators choose the right style.

Styles and variables are related but not identical. A style packages formatting; a variable is a reusable value, often useful for tokens, modes, or values that may change by theme or context. Use the option that fits the project and the Figma features available to you.

Create styles as you go or prepare a small set first. Either way, turn repeated decisions into shared styles instead of recreating near-identical values by eye.

04 · Make a small system

Build a design system that helps

A design system is a shared set of decisions and reusable parts. Start with only what your interface needs; it can evolve alongside the design.

05 · Choose the right container

Frame or group?

Frame

A frame is a container with its own size, layout, fill, clipping, and constraints. Use it for screens, sections, cards, navigation bars, and any object that needs to contain or organize content.

Think: a small artboard inside your screen.

Group

A group makes several selected objects easier to select and move together. It does not provide the same independent container and layout behavior as a frame.

Think: a quick bundle of related objects.

Use frames for most interface structure. Groups are handy for a simple bundle, but convert or reframe the contents when you need layout rules, clipping, a background, or a meaningful parent in the layer tree.

06 · Creating UI

Text properties

Select the text tool, click to create a text layer, and type. In the Design panel, set the font family, weight, size, line height, letter spacing, alignment, and text color. Choose a text style when one exists. Set a text box to resize appropriately: fixed size, auto width, or auto height, depending on how its content should wrap.

Use text roles consistently—page title, section heading, body, and label. Check real copy, not just placeholder text; longer words and translations can change line breaks and layout.

07 · Creating UI

Auto Layout

Auto Layout arranges the children of a frame in a direction, with configurable spacing, padding, alignment, and resizing behavior. Use it for button labels with icons, navigation lists, card contents, form fields, and page sections.

1 Select related layers and add Auto Layout.

2 Choose horizontal or vertical flow.

3 Set padding, gap, alignment, and item spacing.

4 Set resizing: Hug contents, Fill container, or a deliberate fixed size.

5 Change the content to check that the layout responds as intended.

Auto Layout makes a design more robust: a button can grow with its label, and a vertical list can accommodate another item. It does not automatically make a design responsive—set and test the resizing rules that match your intended behavior.

Organize by hierarchy

Keep related content together in meaningful frames. A clear parent-child structure shows how the screen is organized and makes it easier to locate interface elements.

Name layers by purpose

Replace names such as Rectangle 18 or Group 4 with meaningful names. Avoid excessive nesting: each frame should represent a useful layout, component, or content section, not merely add another layer of indirection.

09 · Design system

Create components with intent

A component is a reusable source element. Its instances stay linked to the main component, so a shared change can flow through the interface. Make components for patterns you expect to repeat or maintain—not every shape.

  1. Design and name the element clearly, for example Button / Primary.
  2. Use Auto Layout when the component should adapt to its content.
  3. Create a component, then place instances where the pattern is needed.
  4. Use component properties and variants for meaningful options, such as size or state.
  5. Keep instances connected; detach only when a real exception requires it.

A clear component hierarchy might be Button / Primary and Button / Secondary. Avoid making many variants for differences that belong in separate components or in content.

10 · Prototyping

Prototype by linking views

A prototype connects frames to demonstrate a user flow. Select a button, menu item, or other interactive layer, switch to the Prototype controls, and connect it to the destination frame.

1 Choose a starting frame and set it as the flow starting point.

2 Select an interactive element and drag its connection to another frame.

3 Choose a trigger, such as On click, and an action, such as Navigate to.

4 Set an appropriate transition, then preview and test the flow.

Link the views that tell the story: for example, Home → Menu → Project detail. Test every link, the back path, overlays, and any scrolling behavior in presentation mode. A prototype is a model of the intended interaction, not a substitute for implementing it.

11 · Prepare for handoff

Use Dev Mode

A useful handoff connects the design's structure to the way the interface will be built. Before sharing, name frames and layers, use components for repeated elements, apply shared styles, and remove unused experiments from the final working area.

Use Dev Mode to inspect

Open Dev Mode and select a frame or layer. Review its size, position, spacing, layout behavior, typography, colors, and component context. Check relevant breakpoints or mobile and desktop frames rather than assuming one screen describes every state. Developers can inspect values and copy code snippets where available; the design and implementation still need to be discussed.

12 · Prepare for handoff

Treat CSS as a reference

.primary-button {
  background-color: #26352d;
  border-radius: 0.5rem;
  font-size: 1rem;
  padding: 0.75rem 1rem;
}

Use standard CSS syntax

CSS declarations use lowercase, kebab-case property names. The examples above are background-color, border-radius, and font-size. In JavaScript, CSS properties are often written in camelCase when accessed through an object; ordinary CSS files use kebab-case.

Inspect and adapt generated CSS

Prefer standard properties and avoid unnecessary vendor prefixes. Do not paste a whole block blindly: remove irrelevant values, use the project's existing tokens and class names, and check that the code matches the intended responsive layout.

13 · Prepare for handoff

Use CSS Gen plugin

CSS Gen can help collect CSS for designed elements into a stylesheet. Treat its output as a starting point: plugin options and generated code can vary by version and by selection.

  1. Select the screen or frame you want to prepare. Make sure its layers have clear names and repeated elements use components where appropriate.
  2. Open Figma's Resources or plugins menu, find and run CSS Gen, then choose the option to generate CSS for the selected design or its elements.
  3. Generate or copy the CSS output. If the plugin offers a stylesheet or combined-styles option, use it to collect the selected design's rules together.
  4. Review the result before adding it to your project: keep useful declarations, remove duplicates and unnecessary vendor prefixes, use kebab-case, and replace generic selectors or values with the project's own class names and tokens.
  5. Compare the CSS against Dev Mode and the design at desktop and mobile sizes. Generated CSS does not implement application behavior or guarantee a responsive layout.

Keep the source of truth clear: name and reuse Figma styles or variables in the design, then consolidate the generated declarations into your codebase's existing stylesheet and conventions. Do not paste a fresh block on every run without checking for duplicate or conflicting rules.

14 · Creating UI

Check the styles, not just the screenshot

Select representative layers in Design or Dev Mode and verify the values behind the appearance. A screen can look right at one zoom level but still contain inconsistent styles, accidental overrides, or awkward resizing.

  • Colors come from named styles or variables where appropriate.
  • Text uses the intended text styles, font weights, and line heights.
  • Repeated spacing and corner radii are consistent.
  • Auto Layout padding, gaps, and resizing behave with real content.
  • Desktop and mobile frames are named and checked separately.
  • Components and instances are used consistently; overrides are intentional.
  • Prototype links, starting points, and destinations work.
  • Layer names describe their content and hierarchy.

Final check: select the frame, inspect its properties, then preview the prototype. Share a link with the appropriate access and tell collaborators which page and flow to review.
